# Computer control and vision through Relay

Status: design and phased implementation plan, 2026-11-16. The initial P0/P1
observation provider and capture backends are being delivered under
[`integrations/computer-control/`](../integrations/computer-control/README.md).
Its [review graph](../integrations/computer-control/IMPLEMENTATION.md) separates
implemented/reviewed nodes from live acceptance. No input tools, client controls
or platform extensions are supplied by the initial P0/P1 slice. P2 browser
implementation is tracked in the
[P2 delivery graph](../integrations/computer-control/P2-IMPLEMENTATION.md), including
explicit control opt-in, independent reviews and the continuing live-validation
deferral. Native macOS work is tracked in the
[P3 delivery graph](../integrations/computer-control/P3-IMPLEMENTATION.md) and
[verified readiness continuation](../integrations/computer-control/READINESS-IMPLEMENTATION.md).
The continuation adds SDK host-only local confirmation and scoped live GUI
evidence; its source review does not replace actual native
permission/lock/interference acceptance. Browser and full desktop
control remain intended deliverables; browser-first delivery is a sequence,
not the final scope.

## Goal and architecture

Give agents an observe–act–verify loop over an explicitly selected browser or
interactive desktop. Support structured UI inspection, screenshot reasoning,
pointer and keyboard input, application/window selection and recovery after
uncertain effects. Keep model inference, authority, accounting and durable jobs
on Plowshare; run device access on the machine being controlled.

The proposed module is `integrations/computer-control/`, a reusable provider
library and foreground host built on the public Node SDK, with platform-specific
helpers. TUI and Desktop GUI can embed or supervise that same provider rather
than implement their own computer tools. It must use public SDK contracts and
must not depend on server classes, core tables or private endpoints. A native
desktop helper needs the target user's interactive session; starting a server
container does not provide access to that desktop. Remote placement means the
provider runs on the remote target and connects to an explicitly configured
Plowshare origin. An unauthenticated remote input listener is not part of this
design.

```text
server-owned agent and model
    -> authorized named tool -> Relay invocation
    -> Node ToolProvider on the target machine
    -> target/session controller -> browser or native desktop adapter
    <- physical action outcome + observation
    -> invocation image admission (explicit HTTP binary boundary)
    -> durable SDK result and receipt -> Relay
    -> typed Trajectory observation -> authorized model image input
```

The provider owns translation, target locks, OS permission checks and bounded
local evidence. It does not become another agent scheduler or durable workflow
runtime. An action is one invocation, not an unbounded script generated by the
model. No arbitrary shell, browser JavaScript evaluation or generic native RPC
escape hatch is exposed through these tools.

### SDK foundation and client hosting

The capability is available through SDK-backed tool providers; it is not tied to
a particular user interface. Distinguish the process that supplies capture/input
on a machine from the client that starts or observes an authorized agent run.
TUI and Desktop GUI are the intended first-party local hosts. Their role is to
manage the provider's lifecycle, OS permissions, target selection and stop/release
controls. The computer implementation and Relay behavior remain reusable outside
either client.

| Consumer or host | Intended capability and boundary |
| --- | --- |
| Desktop GUI | Embed or supervise the shared provider on that computer; use checked IPC for local controls. Renderers do not own native input, credentials or an independent tool implementation. |
| TUI | Host the same provider library/process on its machine, using its persistent authenticated SDK connection and native helper where supported. A terminal session alone does not establish desktop permissions. |
| Standalone SDK application or persistent CLI host | Run the reusable provider without either first-party UI, or implement the same tool contract with an appropriate backend. The foreground host is a reference composition of the library, not a privileged execution route. |
| Any SDK consumer initiating server work | Start or observe an agent using an available provider within current grants, bindings and lifecycle. It need not render images locally for the server-side model to receive them. |
| Browser console or another remote client | Use an explicitly available provider on the target machine within its authority. It does not acquire native capture/input locally merely by supporting the SDK or loading a page. |

SDK availability is not automatic cross-client sharing. Interactive provider scopes
belong to their owning authenticated event socket/session; another client cannot
adopt that connection. Cross-session use needs a supported explicit Application
binding or another separately supported sharing lifecycle. Do not invent a new
public sharing API or imply that a GUI-owned interactive provider is usable by
every SDK caller. See [provider scopes](tool-scopes.md).

The initial TUI/GUI composition embeds `ToolProvider` on the host client's
existing authenticated connection and supervises native helpers separately.
A standalone provider process with its own login/socket does not share that
interactive scope, even for the same account. Supervising such a process requires
an explicit supported Application binding, or a separately designed transport
composition preserving the original session. Do not solve this by passing an
interactive routing name to a different socket. P7 must verify the chosen
composition against the real session-bound server checks.

All SDKs expose the general Relay facade, but image-producing parity is narrower:
the initial reusable implementation uses the non-hosted Node `content/1` producer
path. Other SDK consumers can participate through their supported public agent
and tool contracts; direct image production in each language remains a separate
parity gap. Keep browser/OS dependencies in the integration and native helpers,
not the platform-neutral SDK. Any future convenience export from a shared SDK
must be separately scoped SDK work rather than required for this provider.

## Provider interfaces and module ownership

Define narrow typed interfaces before implementing backends:

| Proposed interface | Responsibility |
| --- | --- |
| `ComputerBackend` | Discover configured targets and report actual operation, capture and structured-inspection capabilities. Compose browser/native implementations here. |
| `TargetSessions` | Bind a session to the authenticated call identity and selected target; enforce exclusive target ownership, generation, expiry and release. |
| `ComputerObservation` | Capture bounded pixels and a bounded structured UI snapshot with explicit timing, geometry and completeness. |
| `ComputerInput` | Execute one validated action under a remaining deadline; report whether input was dispatched, partially dispatched or remains uncertain. |
| `ComputerRecovery` | Inspect local physical-work evidence and perform bounded cleanup without executing the original action again. |

These names describe adapter-owned contracts, not new shared SDK operations.
Transport schemas and stored helper messages are converted into validated DTOs
before these interfaces run. Keep vendor objects and raw JSON at their boundaries.
Use the existing exclusive SDK journal for invocation deduplication and publication.
Local helper evidence supplements that journal; it cannot replace a server receipt,
grant authority or make an uncertain invocation executable again.

Proposed source layout: `src/contracts`, `src/provider`, `src/sessions`,
`src/backends/browser`, `src/backends/desktop`, `native/`, `test/` and
`examples/application`. Expose a typed library composition entry point for
embedding and a separate foreground executable; both use the same provider,
backends and journal lifecycle. Client-specific code supplies configuration,
credentials and UI, not duplicated capture/input handlers. Choose package/build
identities during implementation; no Gradle task or distribution is claimed to
exist yet.

## Model-facing tools

Use a configured provider prefix such as `computer_`. Tools use the shared
[bounded schema profile](tool-schemas.md), explicit field allowlists and capability
discovery. Unsupported operations return a useful refusal; they never silently
switch backend, machine, browser profile or focused window.

| Proposed tool | Request and behavior |
| --- | --- |
| `computer_targets` | List only configured, permitted targets and their backend, permission state and capabilities. No arbitrary host scanning. |
| `computer_open` | Select `targetId` and optional configured browser profile/window; acquire a session and return its generation and available surfaces. Capture follows through `computer_observe`. No implicit takeover. |
| `computer_observe` | Supply `sessionId`, generation, surface and optional crop/tree options. Return a fresh frame and/or structured snapshot. |
| `computer_windows` | List bounded window/tab metadata for that session. |
| `computer_focus` | Select a returned window/tab reference explicitly; return the resulting focus and observation. |
| `computer_pointer` | One `move`, `click`, `double_click` or bounded `drag`, using a frame point or element reference. Buttons and modifiers are allowlisted. |
| `computer_type` | Bounded Unicode text with an explicit expected editable target/focus. Report insertion mechanism; do not silently use or overwrite the clipboard. |
| `computer_key` | One allowlisted chord, or capability-gated press/release. Track held inputs for cleanup; enforce a maximum hold duration. |
| `computer_scroll` | Frame/element target, horizontal/vertical deltas and explicit units. Backend conversion is reported. |
| `computer_navigate` | Browser-only URL navigation with validated scheme/origin policy; return the observed final location. Browser redirects and new tabs remain inside configured policy. |
| `computer_close` | Stop session intake, settle/fence physical work, release held inputs and relinquish ownership. Does not promise to undo earlier actions. |

All tools derive project/account/run identity from validated `ToolCall`, never
model arguments. A session belongs to that identity, target and provider generation;
an opaque ID alone is insufficient. Delegation or another run does not inherit
the session implicitly. Restart invalidates old session/element/frame references.
Reopening a session does not resolve an earlier UNKNOWN invocation.

The first release has no arbitrary multi-action batch. Browser forms, custom
canvases, menus, dialogs and drag/drop use these same bounded primitives. File
upload/download, clipboard access, application launching and credential injection
require separate explicit capabilities and policies before being advertised.
They are expansion work, not hidden behaviors of `type` or navigation.

For example, a point click request has this adapter-owned shape (illustrative IDs):

```json
{
  "sessionId": "session-example",
  "generation": "generation-example",
  "action": "click",
  "target": {
    "kind": "point",
    "frameId": "frame-example",
    "x": 320,
    "y": 180
  },
  "button": "left"
}
```

An element target instead contains `kind: element`, `snapshotId` and `elementId`.
The validator rejects mixed target fields and coordinates outside the named frame.
Authenticated account/project/run identity, raw native handles, transforms and
deadlines are not model-selectable fields. Define and test the exact shared-schema
representation in P0; do not assume unsupported JSON Schema union keywords are
available.

### Observation and action result contract

Serialize a validated provider-owned `computer-control/1` metadata DTO into a
TEXT part, followed by admitted image parts. This is an adapter result format
inside `content/1`, not a new Relay protocol or shared platform DTO. Bound metadata
to 12,000 UTF-16 units and separately enforce the complete encoded envelope's
32,768-unit ceiling. The metadata is JSON text inside another JSON envelope, so
measure escaping and envelope overhead rather than counting text fields alone.
Reserve that overhead and bound variable-length fields; trim optional tree data
at DTO boundaries before final serialization, explicitly
marking truncation. Validate the final SDK result before returning it. Never cut
serialized JSON or discover an avoidable size violation only after input: the
SDK maps invalid handler results to UNKNOWN. Keep a prevalidated minimal outcome
that fits the pinned invocation fields if optional observation data will not fit.
Expose explicit bounded subtree reads rather than treating an incomplete tree
as complete.

Metadata includes:

- Session, generation, target, surface, frame/snapshot IDs and capture timestamps.
- Backend, focus, URL/application/window identity as applicable, with sensitive
  titles or fields excluded under configured disclosure policy.
- Image slot, encoding, pixel dimensions, crop, coordinate transform and layout
  generation; separate pixel and tree timestamps when capture is not atomic.
- Element references, roles, accessible names, permitted states/actions and
  bounds when available. Missing tree support is explicit; pixels still work.
- Original invocation ID, action outcome, observation outcome, elapsed time,
  truncation and actionable failure code when relevant.

Action outcomes are `NOT_DISPATCHED`, `DISPATCHED`, `PARTIAL` or `UNCERTAIN`.
`DISPATCHED` means input delivery was established at the adapter boundary, not
that a purchase, save or other application operation succeeded. Verification
reports separate evidence such as changed text, URL or pixels. Do not turn an
accessibility action's return value into a claim about business completion.

Default to a fresh post-action observation. Reserve time for it before starting
input. An observation failure after known input delivery can return `COMPLETED`
with explicit action/observation outcomes and text only. Never describe that as
an entirely successful interaction. If input may have happened but delivery is
unresolved, return `UNKNOWN`, which currently cannot carry images. A later
`computer_observe` is a new read; it does not repeat or settle the original action.
`REJECTED` is reserved for a known refusal before input, not a partial type/drag.
If the helper proves exactly which input was delivered before it stopped, use
`COMPLETED` with action outcome `PARTIAL`, the bounded delivered extent and an
explicit incomplete-operation explanation. If that extent or physical settlement
is not established, use `UNKNOWN`/`UNCERTAIN` and keep the target fenced. Neither
case authorizes replay of the original action.

### Coordinates and stale observations

Model coordinates are integer pixels in the returned image, with top-left origin.
The provider applies the recorded transform into browser viewport CSS coordinates
or native desktop coordinates. Report the full transform, crop origin, per-display
scale and layout generation; a single scale factor is insufficient for mixed-DPI
or rotated displays. Native desktop origins may be negative. Capture one display
or window per frame initially rather than inventing one uniform desktop scale.

Every targeted input names a frame or structured snapshot from its session.
Reject expired references, changed layout generations, closed targets and
unexpected focus before input. Browser element references are opaque bindings to
the observed document/element, invalidated by navigation or replacement; do not
re-resolve an old reference to a different element with matching text. Native
element bindings are similarly session-scoped. A layout/focus check reduces races
but cannot freeze a third-party UI. Return `STALE_OBSERVATION` and request a new
observation instead of silently retargeting. A model-provided freshness claim is
not evidence.

## Browser and full desktop backends

### Browser

Use a pinned Playwright Node library behind the browser interfaces. Start with
provider-owned Chromium contexts; attaching to an existing browser/profile is a
separate opt-in capability with explicit endpoint/profile configuration. Do not
reuse the machine owner's personal browser session by default.

Implement screenshots, bounded accessible structure, element references, tabs,
navigation and pointer/keyboard operations. Playwright's
[actionability checks](https://playwright.dev/docs/actionability) help establish
element readiness; retain them and pass the remaining deadline explicitly.
[Screenshot scaling](https://playwright.dev/docs/api/class-page#page-screenshot)
distinguishes CSS and device pixels. Neither feature supplies Plowshare session
authorization or invocation recovery. ARIA snapshots are useful structure, not
durable action handles; the adapter owns the element-reference mapping.

Treat dialogs, cross-origin frames, popups, downloads and navigation as explicit
state transitions. Browser control cannot reach browser chrome, native file
pickers or other desktop applications; crossing that boundary requires an
explicit native target, not automatic escalation. Use isolated contexts for
parallel browser sessions where their resources are genuinely independent.

### Full desktop

Ship macOS first, then independent Windows and Linux backends under the same
contracts. A native helper exposes a versioned typed local protocol with bounded
messages over an authenticated/private local channel. Launch only a configured
executable with an argument vector; never interpolate model input into a shell.
The Node process owns Relay and credentials; the helper receives only the exact
targeted operation and remaining budget, not Plowshare tokens.

| Platform | Proposed implementation and acceptance boundary |
| --- | --- |
| macOS | ScreenCaptureKit for display/window capture, Accessibility for structured UI/actions and native event injection for pixel input. Validate screen-capture and accessibility permissions separately using the packaged helper identity. Test signed packaging, permission denial/revocation, locked sessions and multi-display transforms. [Apple capture documentation](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) is the backend reference; exact supported OS versions are established during the native spike. |
| Windows | Native capture, UI Automation and `SendInput`, with DPI-aware geometry. Microsoft's [SendInput contract](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) limits injection by integrity level; report blocked/elevated targets and secure desktops explicitly. Do not auto-elevate. Pin a supported Windows/capture matrix during the spike. |
| Linux | Separate Wayland and X11 capability profiles. Prefer the [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) with ScreenCast integration on Wayland, and evaluate AT-SPI for structure. Portal sessions require the backend's consent flow; support varies by compositor. An X11 implementation is separately tested and explicitly selected, not a silent Wayland fallback. |

“Full desktop” means ordinary applications and surfaces available to the logged-in
session under OS permissions. It does not promise bypass of secure input,
protected content, lock screens or privilege boundaries. Capture availability
does not establish input or accessibility availability. Missing structured UI
support must not prevent supported pixel control.

## Authority, concurrency and lifecycle

Relay grants remain the server admission boundary. Use distinct exact grants for
observation and mutation tools, with optional provider-local restrictions on
targets, apps and browser origins. Such restrictions only narrow server authority.
Connecting a provider or enabling `dynamic` grants no broader machine access.
Do not advertise a wildcard as read-only: it covers future tools from the provider.

The baseline is explicitly authorized session control, not mandatory confirmation
for every key or click. Current Personal approval policy does not cover general
Relay tools. A local opt-in/stop UI can be provider-owned, but must not be presented
as Plowshare's Personal approval flow. Policies that require a server human
approval before an external action are blocked on the separately scoped gap below.
Screens and accessibility text are untrusted task data, never instructions that
can authorize a new target, policy change or privilege increase.

One broker owns each OS interactive session across provider bindings/processes.
Acquire an OS-level exclusive lock for the desktop resource, not just a JavaScript
mutex per tool. Browser/native paths that share the physical desktop join that
same lock domain. Pure isolated browser contexts may use independent domains.
Session ownership prevents interleaving actions by different runs; a bounded
operation lock also keeps an observation/action from racing another invocation.
OS locks coordinate cooperating providers, not arbitrary humans or applications.
Unexpected local input/focus changes invalidate affected references and pause
intake where the backend can detect them; never claim universal interference
detection.

Lifecycle: `OPEN -> ACTIVE -> CLOSING -> CLOSED`, with `FENCED` reachable whenever
execution or cleanup cannot be established. Session expiry prevents new input;
it does not free a target still doing physical work. A local stop immediately
blocks intake and requests bounded cleanup. Release only keys/buttons owned by
the provider. Persist a small outstanding-work marker before dispatch to a helper;
after a crash, establish helper quiescence or keep the target fenced before
opening a replacement session. Do not replay the action to discover its outcome.

The SDK saves `executing` before handler execution and READY before publication.
Preserve this ordering. A handler/helper crash, lost upload or publication reply
keeps the original invocation and admission-slot identities. Reconcile receipts
without recapturing, retyping, clicking again or publishing under a new UUID.
If evidence is insufficient, leave UNKNOWN visible. Local helper evidence cannot
rewrite an immutable SDK result already settled as UNKNOWN.

## Bounded work, images and configuration

All limits are validated, finite deployment settings. Proposed defaults:

| Unit | Default and owner |
| --- | --- |
| Target/status reads and session controls | 2 seconds, including lock admission and result construction. |
| Observe or action-with-observation | 10 seconds, justified by capture, encoding and binary transfer; browser navigation also uses this budget. A slower operation needs an explicit configured limit within the Relay declaration ceiling. |
| Cleanup/drain after cancellation | 2 seconds; on failure fence the resource instead of falsely releasing it. |
| Lock admission | At most 250 ms and never beyond remaining operation time; return busy rather than accumulate an unbounded queue. |
| Frame freshness | 5 seconds, plus layout/focus/document checks; configurable and never a guarantee against UI races. |
| Idle session | 60 seconds; renew through explicit bounded activity. Expiry triggers cleanup, not a 60-second held request. |
| Capture | One observation image per result initially, longest edge at most 1600 pixels and at most 1 MiB encoded, additionally constrained by actual server image/pixel limits. PNG for crisp UI; verified JPEG/WebP may be selected explicitly. Report resizing. |
| Structured UI | At most 200 nodes and the metadata text bound; explicit truncation/subtree selection. |
| Input | At most 4096 UTF-16 units per type operation; at most 128 drag points and a one-second drag/held-input duration initially. |

At admission derive a local monotonic budget from the earlier of the validated
call deadline and configured declaration limit. Queueing, input, settling,
capture, encoding and upload share the remaining time. Reserve an observation
allowance before starting input; do not reset the timer at each stage. Settlement
means a bounded backend condition, not waiting indefinitely for network idle.
Publication/cleanup retain the SDK lifecycle; do not claim a universal two-second
end-to-end Relay guarantee.

The current [Node host](../sdk/node/src/tools.ts) races a promise against a timer;
it does not abort physical execution. Implement adapter-owned cancellation and
resource fencing, using the public `ToolHost.execute` seam where necessary.
The [image uploader](../sdk/node/src/image-admissions.ts) uses a fixed 60-second
HTTP timeout; supply its injectable fetch with an earlier abort bound to the
remaining operation deadline, preserving no-redirect/no-retry behavior. Test
physical settlement and exclusion of late successful handler output, not only
promise rejection. Publishing the SDK's retained UNKNOWN after timeout is still
part of recovery; it must not be suppressed as if the invocation never existed.

Image bounds are independent of downscaling: each occurrence still incurs the
profile's reservation. Current reconstruction permits at most 16 retained image
occurrences and 20 MiB of unique retained bytes; model/prompt limits may reject
earlier. A result has at most four distinct image slots. Do not assume a provider
can remove old frames from the active context or account for other providers'
images. Initially cap this provider at eight image-bearing results per run,
retain the counter across local recovery and refuse further captures clearly;
this is a conservative local bound, not proof that the complete prompt fits.
Check the cap before starting an action that promises an image. Reopening a
session must not reset it. Context previews omit pixels and transient
additions and are not provider-payload receipts.

Reuse existing turn/fold/reference policies and independently retained Trajectory
claims. Do not delete audit evidence to lower model context use. Arbitrarily long
interactive sessions remain unaccepted until rolling context behavior is decided
and verified. Until then, acceptance covers short bounded tasks and explicit
budget exhaustion; no hidden automatic conversation restart is permitted.

Required deployment configuration includes server origin/credential source,
project/provider binding, target allowlist, browser profiles or native helper,
private journal/lock locations, operation/cleanup budgets and capture/disclosure
policy. Keep these outside source and manifests that agents can edit. Validate
missing values before connecting. Reuse one authenticated SDK connection for
catalogues and polls, with bounded renewal and shutdown. Start with non-hosted
Application providers or a persistent interactive scope; hosted worker catalogues
currently refuse `content/1`.

Raw images belong in admitted blob storage, not logs, exception messages or a
second screenshot archive. Do not put typed text or credentials in diagnostic
logs. Tool arguments, including typed text, still enter the existing private SDK
journal and server invocation/history retention; this design does not provide a
secret-input channel. If OS/browser capture filtering is configured, apply it
before upload and report exclusions; masking pixels alone does not remove
matching accessibility text. The existing
SDK file journal caps receipts at 1000 and enforces 2,000,000 serialized UTF-8
bytes through its shared atomic writer and on reopen. Those per-save checks do
not reserve space for a larger READY/result checkpoint after an action. The
provider's `ToolJournal` composition must reserve serialized UTF-8 capacity for
the full receipt lifecycle before admitting input, including executing, READY,
publication and UNKNOWN checkpoints, and refuse admission when that reserve will
not fit.
Preflight count and byte capacity before SDK saves, preserving its original
receipt identities and recovery semantics. There is no automatic safe pruning;
retain uncertain receipts and use a reviewed archival strategy preserving
deduplication before claiming continuous service.

## Platform gaps and disposition

These are capability gaps, not authorization to implement core changes as part
of the integration. Any selected platform extension needs its own authorized
task and ADR covering SDK-only alternatives, authority/lifecycle, compatibility,
rollback and tests under ADR 0001.

| Gap | Consequence | Delivery disposition |
| --- | --- | --- |
| Rolling image selection in the active model context | No public provider operation replaces old screenshots with the latest frame(s). Long action loops can exhaust image count/context even with small JPEGs. | Blocks long-session acceptance. Separate platform proposal for bounded projection selection preserving audit claims; existing compaction and provider task caps are the initial limits, not equivalent functionality. |
| General external-tool approval | Relay authority does not route arbitrary tools through Personal per-action review. | Existing explicitly granted control can proceed. A product requirement for server human review blocks that mode pending a general platform decision; provider-local consent is only local policy. |
| Immediate server-to-provider cancellation/revocation notification | Server stops waiting but cannot promise physical input stops immediately; already admitted effects cannot be undone. | Provider cancellation, local stop and fencing are required. Stronger immediate remote cancellation remains separate platform work; do not advertise it. |
| UNKNOWN image/result recovery | UNKNOWN/REJECTED are text-only; invocation reads and `result_read` do not redeem pixels into model input. | Use a separate authorized observation. Do not retrofit images into settled UNKNOWN results or automatically replay the effect. Typed redemption would be separate platform work. |
| Hosted typed results and other producer SDKs | Non-hosted Node has the required image producer path; hosted worker catalogues refuse it and other producers remain text-only. | Ship the direct Node provider first. General hosted/content parity is optional separately scoped platform work. |
| Native client management | No computer-target/session picker, local permission setup, takeover or stop UI is implemented by existing MCP controls. | Foreground provider CLI/local stop first. Dedicated Desktop/TUI hosting controls are a later client deliverable; reuse public scopes without claiming existing MCP screens manage this provider. |
| Universal completion deadlines and journal archival | SDK timers do not prove remote abort; the supplied journal eventually fills and per-save size checks do not reserve future result capacity. | Adapter-owned remaining budgets, abortable helpers, physical fencing and reserved journal capacity before input first. Report any required public lifecycle/archival capability as a separate gap; do not rely on post-effect save failure as admission control. |

Backend-specific permission, compositor, accessibility and packaging limitations
are adapter work, not reasons to change core. Exact browser/OS support and model
reliability remain unverified until the corresponding acceptance phase passes.

## Phased delivery and dependencies

The roles below are assignments for future implementation slices, not claims that
an independent review has occurred. Each node closes only after its implementer
and a separate reviewer agree on the actual diff and evidence. Keep implemented,
verified/reviewed, merged, deployed and live-validated states separate. Platform
nodes use separate authorization; deployment is not implied by code completion.

| Phase / dependencies | Deliverable and ownership | Required acceptance evidence |
| --- | --- | --- |
| P0: contracts and backend spikes | Integration implementer; independent integration reviewer. Finalize DTOs, tools, budgets, OS/browser matrix and physical lock identity. Probe browser and macOS capture/input/permission boundaries against controlled fixtures; no product action tools yet. | Strict schema rejection, geometry round trips including crop/rotation/mixed scale, stale reference refusal, capability/permission matrix and recorded unresolved platform gaps. Pin native/library versions after the spikes. |
| P1 after P0: observation transport | Integration implementer; independent SDK/image-path reviewer. P1 is a transport milestone, not completion of computer control. P2 plus P3 provide
the first browser-and-desktop product slice. P4 establishes bounded operational
readiness. Long unattended tasks require the relevant P5 context/lifecycle gates;
Windows/Linux support requires P6 and cannot be inferred from shared interfaces.

### Verification strategy and release evidence

Default tests use fake SDK connections, capture/input backends, clocks and private
temporary journals. Cover malformed/extra fields, foreign account/project/run
references, expired sessions, revoked availability, oversize trees/text/images,
coordinate boundaries and races. Include worst-case nested JSON escaping and
UTF-8 journal size, full receipt transitions near the journal ceiling, refusal
before input when capacity cannot be reserved, and exact partial-input reporting.
Test that timers stop new work, a late helper still owns its target and cleanup
cannot silently un-fence uncertain execution. Test embedded and subprocess hosts
against session ownership; matching accounts alone must not adopt a foreign scope.

Use controlled browser/native fixture applications with counters so duplicate
clicks, partial typing and input ordering are observable. Fault-inject around
intent, dispatch, screenshot capture, upload, READY and publication. A lost
response after possible input must never become evidence that retry is safe.
Screen changes alone do not establish which invocation caused them.

Run targeted adapter checks and `integrationBoundaryCheck`, followed by the
repository checks appropriate to the implemented slice. Native tests require the
explicit OS/session environment. Routine verification must not enable real
PostgreSQL or `dockerSmoke`; any separately authorized persistence change needs
its own smallest relevant `full-db` selection and database-specific rationale.
This documentation change requires link/diff checks, not database tests.

For live validation retain sanitized source revision, backend/OS/library and wire
model/profile versions, configuration limits, invocation IDs, outcomes and test
results in authorized evidence storage. Prove browser control and desktop control
independently, including remote provider placement and a real model consuming
screenshots. A healthy provider/catalogue, a mocked request or a correct model
caption alone does not establish the full observe–act–verify lifecycle.
