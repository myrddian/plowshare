# HA-11 — Installable SDK-based Assist component

Implementer: `ha_packaging_sdk_implementer`. Independent reviewer:
`ha_packaging_sdk_reviewer`. Implementation passed coordinator-owned checks and is ready for independent
review; this note does not claim review acceptance, deployment or live validation.

The obsolete native-system-role/cache publication mechanism is removed, including
its configuration/setup guards, abort strings and test bypasses. Real setup and
configuration now exercise the already-reviewed SDK-only Conversation and AI Task
paths. This does not add native role semantics: exact HA prepared text remains
ordinary task/user input under the selected server agent's authority/retention.
No SDK, core, shared runtime, schema, entity, structured parser, journal or gateway
semantic changes are part of this node.

`package.py` stages the production component through the same helper used by the
HA fixtures. It includes every current public Python SDK file/resource unchanged,
its license and a private namespace marker. HA manifest requirements must exactly
match SDK dependencies. Source vendor trees, overlapping source/staging paths,
symlinks/special files, hidden runtime files and unexpected file types are rejected.
Generated bytecode/cache directories are excluded. Builds cannot overwrite source
checkout files: only the Assist build directory or external output is admitted.

The ZIP contains the standard `custom_components/plowshare` install topology,
artifact-local install/profile instructions, all three unchanged independently
reviewed Application profile roots, and a SHA-256 contents manifest. Sorted files
and fixed ZIP metadata make identical inputs deterministic. The entire stage and
ZIP write finishes before atomic output replacement; a failed stage/write retains
an existing artifact. Generated vendor trees and built ZIPs are not checked in.

The narrow `PROVIDER-HOST.md` opening status sentence now points to the separate
component; its outbound host configuration and semantics are unchanged.
Documentation explains explicit route/credential/project ownership, independent
profile grants, optional supplied-data text/structured AI Task, HA speech engines,
ordinary prompt semantics and unchanged prefix-cache behavior. It records finite
budgets/four physical owners per profile, durable intent, no replay/automatic
cancellation, pending reconciliation, token fingerprint fences, legacy local-map
quarantine, unknown/foreign/expired HA chat-ID behavior, process-restart limits,
and preservation of private journals during replacement/rollback. The validated
baseline remains HA 2026.9.4/Python 3.14; the target instance version is unverified.

New acceptance fixtures build/extract a real CLI archive outside the checkout,
compare complete SDK/resource/license and Application profile bytes, check archive
namespace/content hashes/local documentation links, and run a fresh isolated
Python consumer importing HA entities and SDK Ex codecs/resources from that
archive. Its configuration form and invalid-input rejection require no SDK
connection or private journal. Failure/hygiene cases exercise dependency mismatch,
source-output overlap, hidden files, symlinks, vendor contamination and atomic
write failure. Additional actual HA reconfiguration fixtures verify token/timeout
updates retain receipts and route changes refuse before SDK/reload work. Existing
setup/recovery/gateway suites now run without readiness bypasses.

The coordinator coauthored the protected `.agents/guides/integrations.md`
readiness paragraph: the SDK component is available, HA text has ordinary
task/user semantics without special compaction guarantees, and cache awareness
is advisory rather than an availability gate. No platform policy changed.
`custom_components/plowshare/availability.py` is deliberately absent/deleted;
acceptance must record that absence, not hash a replacement fidelity flag.
