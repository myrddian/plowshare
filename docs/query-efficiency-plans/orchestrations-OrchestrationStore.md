# OrchestrationStore

Status: proposed; no runtime implementation. Baseline: `fc36351f239b62984363ababaa1de1139402aafb`.

Cache mechanics and recovery follow the [shared strategy](../query-efficiency-and-cache-design.md#server-reuse-and-tracked-database-dtos).

This broad owner serves run creation/receipts, state CAS transitions, messages/questions, counters/caps, delivery acknowledgements, live/child/caller lists and stall timing. `Orchestrations`, delivery workers and `StallSweep` may repeatedly hydrate large run records to obtain a few fields. `quietSince` recursively scans descendant conversations/entries per run; live sweeps can multiply that work. Measure those caller sequences before claiming a dominant cost.

Split specialist typed query capabilities for run summaries, mutable transition state and message pages while keeping transaction ownership intact. Pass known `OrchestrationRecord` snapshots into helpers and use existing counter `RETURNING` patterns for state transitions whose callers reload. Batch quiet/activity evidence across live runs with a bounded recursive query rather than per-run descendant scans. Paginate messages and large recovery lists. V48/V51/V52 already provide live, caller and live-child indexes; compare actual caller/project/created+ID, message ordering and undelivered predicates before targeted partial/composite additions. A typed transition/question routine may combine proven trips but must preserve row locks, pending-cap capture and exact receipt reconciliation.

Cache immutable message bodies, pinned definition descriptors and explicitly versioned historical run views; keys include database/run/account/project/projection and source generation. Never cache lifecycle admission, pending caps, live child exclusion, counters, stall evidence or delivery claims as authority. Every transition, question/answer, placement, counter, delivery and resume writer invalidates run/message/caller/parent/live collections after commit. Source versions and cross-owner durable change recovery are prerequisites; a cached terminal view must account for authorized resume. Notifications can wake delivery/sweeps, retaining durable rows, CAS and reconciliation.

Mock per-action hydration and per-sweep query budgets. Focused PostgreSQL tests cover batching equivalence, receipt/CAS/answer races and new index plans; client refresh and async read dispatch are separate delivery layers.
