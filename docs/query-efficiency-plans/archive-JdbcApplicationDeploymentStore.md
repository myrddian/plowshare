# JdbcApplicationDeploymentStore

Status: Proposed. Source baseline: `fc36351f239b62984363ababaa1de1139402aafb`.

[The deployment store](../../plowshare-server/src/main/java/io/aeyer/plowshare/server/archive/JdbcApplicationDeploymentStore.java#L106) serializes activation with identity and project locks, reconciles a request receipt, compares the current deployment head to `expectedRevision`, retains releases, changes project placement, activates identities/acting grants and registers first-source schedules in one unit of work. `status` already pairs head and bounded catalog in one SQL snapshot. Application deployment configuration selects this implementation.

Confirmed waste: `commit` loads the previous active `Retained` release for destination/writable-area validation, then loads that same active release again when calling `activateDeployment` (lines 128 and 143). Reuse the first typed value within the transaction. Carry resolved project identity into cooperating owners rather than repeating name resolution. Preserve authoritative receipt/head checks under lock; a previously read status cannot replace `expectedRevision` comparison. Narrow `release` from `s.*` to mapped columns. [V134](../../plowshare-server/src/main/resources/db/migration/V134__application_deployments.sql#L3) supplies release/head/receipt keys; evaluate `(project_id,created_at DESC,revision)` only if retained-catalog sorting is material. The active-first sort must continue including the head even beyond 100 releases. A stored activation routine is optional only for cohesive database work; filesystem admission and source validation remain their owning capabilities.

Cache immutable `Retained` values keyed by database, project identity, release UUID and projection/schema version. Separately track status/head/catalog by durable deployment generation; release UUID alone cannot version a mutable catalog. Invalidation dependencies include release membership, deployment head, project placement/boundary, acting/identity activation and schedule-source registration. Publish after the whole transaction commits; every database writer must contribute change evidence. Never cache activation locks or replace live current authority. Deployment DTOs containing paths also require current FileStore configuration/filesystem validation; cached paths grant no access. On reconnect bypass mutable deployment projections until durable recovery; use the shared bounded LRU.

Deliver operation-local reuse first, then projection/index improvements, then versioned tracking. Mock one previous-release read per changed-head activation, stable expected-version refusals and unchanged first-source ownership. Focused PostgreSQL tests are justified only for changed SQL/notifications: two activators, receipt mismatch, rollback across dependent owners and status ordering. No deployment or implementation is performed by this plan.
