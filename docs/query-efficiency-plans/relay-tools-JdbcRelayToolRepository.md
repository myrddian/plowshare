# JdbcRelayToolRepository

Status: Proposed. Source baseline: `fc36351f239b62984363ababaa1de1139402aafb`.

[Relay tool persistence](../../plowshare-server/src/main/java/io/aeyer/plowshare/server/relay/tools/JdbcRelayToolRepository.java#L34) verifies retained inference ownership for ancestry, commits immutable invocation intent plus first publication, reconciles existing intent under row lock, and records exactly one matching completion. ProjectRelayToolInvocations and hosted scope authority coordinate execution. [V132](../../plowshare-server/src/main/resources/db/migration/V132__relay_tool_invocations.sql#L2) makes invocation ID primary and preserves intent beyond broker retention; absence of a Relay publication never authorizes replay.

`submit` for hosted tools first reads existing intent before selecting credentials, then takes the authoritative lock; that repetition has an explicit immutable-credential/idempotency reason. Retain it unless a redesigned typed lock/read path can avoid needless decoding without pinning new credentials on retries. On first insert, `locked(intent)` rehydrates the same retained request/definition; evaluate `INSERT ... RETURNING` and a conflict-path locked read, accounting for stored hosted pin differences and concurrency. `finish` already returns `new Stored(retained.intent(), result)` without reloading: keep this good reuse. Topic registration is repeated per new invocation; measure it in the owning Relay contract before assuming it is removable. A stored submit/finish routine is useful only if it preserves exact identity/fingerprint checks and atomic publish/receipt behavior. Existing primary-key lookup needs no speculative index; ancestry joins should be profiled with current inference-ownership keys.

Separate immutable intent/completed result from mutable pending completion and live hosted authority. Initially keep mutation decisions and hosted credential/pin DTOs out of shared caching. A sanitized completed-result projection can be keyed by database/project/account/invocation/fingerprint/projection and completion version; retain the precise committed identity. Pending result absence needs a durable generation and must be invalidated on finish. Dependencies include invocation insertion/completion, project deletion, current account/scope visibility and any sanitized definition/hosted generation exposed. Every repository/database writer emits after-commit invalidation; rollback never publishes completion. Current grants, worker/credential authority and row locks remain required for effects. Reconnect bypasses uncertain pending/inspection state until durable recovery; use bounded shared LRU with result-size limits.

First optimize returned projections and reuse existing Stored values, then consider sanitized result tracking. Notifications wake result readers, with durable intent reconciliation after disconnect; they never trigger resubmission. Mock repeated-submit no credential reselection/publication, same-result reuse and conflicting completion. Changed SQL requires focused PostgreSQL concurrent submit/finish, fingerprint conflict, publication rollback and completion/invalidation races. [Delivery](delivery.md) defines shared foundations.
