# ProjectStore

Status: Proposed. Source baseline: `fc36351f239b62984363ababaa1de1139402aafb`.

[ProjectStore](../../plowshare-server/src/main/java/io/aeyer/plowshare/server/archive/ProjectStore.java#L489) persists project identity, legacy workspace/lending/exclusions, client attachments, server/Application placement, creation/first membership and listings. It implements several capability interfaces consumed by definitions, filesystem fencing, deployment, client views and project APIs. Effective roles belong to ProjectMembers. `find` resolves FileStore aliases and verifies directories, so query time and filesystem resolution time must be measured separately.

Confirmed extra work: `createServer` invokes `defineLending` then changes project type/placement and refetches; `place`, `activateDeployment` and `attachClient` also update then select. Prefer typed `RETURNING` projections where they preserve conditional guards, with explicit alias/directory validation once at the appropriate boundary. Carry the already resolved project/ID through `withCreator`, deployment and membership operations. `effectiveExclusions(ProjectRecord)` already supports reuse; callers holding that row should avoid its name-based overload. Keep `refuseLegacyPlacement` and current placement/FileStore checks as concurrency/authorization fences where needed. Some lend/unlend/move SQL already returns the row: preserve those savings. Unique name and ID lookups are appropriate; optimize allFor's authority candidate set or session-prefix listing only after measuring cardinality/selectivity. A stored creation/placement function could consolidate database steps, but cannot replace current host filesystem validation.

Separate immutable stored placement metadata from host-resolved paths and effective access. Track stored ProjectRecord-like DTOs by database/project ID, projection and complete durable project generation; `defined_at` is not yet a comprehensive version across every writer. Lists add account/session/filter/cursor and membership generation. Resolved projections depend additionally on FileStore configuration generation, mandatory exclusions, host identity and filesystem availability, which database NOTIFY alone cannot track. Re-resolve/refuse unavailable aliases rather than serving stale roots. Cover define/lend/move/rename/forget/client attach, deployment, personal initialization, Application boundary, project registration and membership/authority writers in after-commit invalidation, including absent-to-present/list membership. Project IDs and JdbcProjectDirectories must share one resolution cache. Current authority and workspace fences remain live; never cache them as permissions. Reconnect bypasses uncertain namespaces, using bounded shared LRU.

Deliver operation reuse/returned rows first, measured list SQL second and stored-metadata tracking third. Mock one resolution per consistent filesystem operation and no stale-root fallback. Changed SQL requires focused PostgreSQL concurrent creation, first-manager atomicity, placement guards, rename/forget invalidation and rollback tests; filesystem alias changes need focused non-DB boundary tests. No persistence or filesystem behavior changes in this plan.
