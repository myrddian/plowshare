# JdbcInformationProjectionRepository

Status: Proposed; no implementation. Baseline: `fc36351f239b62984363ababaa1de1139402aafb`.

[Source](../../plowshare-server/src/main/java/io/aeyer/plowshare/server/information/JdbcInformationProjectionRepository.java#L33) implements prepared physical projection reuse for content revision. `prepare` first reads an actor/request receipt; otherwise `capture` locks slots, authority, resource/revision/head, stages and projection rows. It checks stage completeness/bounds, hashes revision/material/staging/report/input/citation state and persists a manifest. `copy` recaptures the manifest before copying a new explicit-only revision with remapped hierarchy/vector identities, inputs/reports/citations, stage provenance and request receipt. These are retained approval and concurrency checks, not ordinary repeated read defects.

There are nevertheless many statements: completeness checks run per stage, material-size scans and later per-table hashes inspect overlapping projections, and stage rows are loaded for locks then reloaded. Reuse selected typed stage/header rows within the same locked transaction. Compute bounded completeness, size and per-projection hashes together using a typed table-returning function or one CTE bundle, ensuring size bounds apply before aggregation. Do not reuse a pre-hook manifest as proof after hook execution; recapture/recomparison prevents stale approved copying. Keep extraction-only fallback for oversized corpus and dependency-aware reuse selection.

[V144](../../plowshare-server/src/main/resources/db/migration/V144__information_projection_reuse_policy.sql#L15) records exact origin provenance; [V145](../../plowshare-server/src/main/resources/db/migration/V145__information_reuse_prepared_candidates.sql#L2) retains preparation identity. Existing document/paragraph/staging keys are the starting point. Profile actual bounded projection scans before adding indexes; hashing all material inherently reads it. A stored routine must preserve slot-before-resource lock order, optimistic conflict outcomes and exact fingerprint mapping.

Do not cache captured manifests as current proof, completeness checks, locks or copy admission. Retained prepared display DTOs can be tracked by database, actor/request/fingerprint, exact source revision/generation, manifest hash, configuration and binding. Every source/material/staging/slot/report/input/citation mutation, catalogue deletion/rebuild/sanitization, preparation/copy and external writer invalidates relevant display dependencies after commit. Generation alone is insufficient for all material changes. Cache immutable projection content by exact identity/version only after current authority and deletion fences. Use the proposed tracked DTO/LRU with byte/dependency bounds and durable notification recovery; broad namespace invalidation is acceptable for high fan-out.

Mock tests should prove reuse within one capture, constant stage-query counts and retained mandatory recapture after hooks. Future focused PostgreSQL tests cover snapshot hash equivalence, remapped identities, vector staging validity, lock ordering, source mutation during approval, atomic rollback and notification races. Keep this work separate from implementing the shared cache foundation.
